## 0. 结论摘要

1. **项目定位**：15 MW 风机在 DNV Bladed 闭环下的分层残差控制研发工程，不是已验收的控制产品。控制链为 `状态识别 → B4 分区基线 → Actor 有界残差 → 安全投影 → UDP → Bladed`，学习器为 TD3+BC，物理载荷模型仅以只读 shadow 运行。
2. **当前状态**：活动发行 R2 为“离线开发候选”，物理启动被阻塞；最近一次完整诊断训练（2026-09-19，23 风况 × 4 轮 × 600 s）物理目标未达成——电量相对 PID **−0.712%**，三叶根 My 峰值分别 **+4.07% / +4.78% / +5.02%**（[深度分析](./旧版B4残差TD3_BC_state20实验深度分析_20260919.md#L5)）。
3. **场景关系**：**4×4（16 slot）与 23×4（92 slot）是两条并列的实验验证场景，不是新旧版本冲突**。4×4 用于快速联调与合同验证，23×4 用于全风况训练与指标评估；两者共用同一套 state20/B4/BC/安全控制与只读影子。
4. **运行约束**：Bladed 运行在 Windows 端，闭环必须人工操作；本机只能在 Linux 端做离线独立验证。通信层（IP/端口/UDP/DLL）已由使用者确认验证通过；仍缺的是 L2 身份/排程证据与 L3 性能/验收证据。
5. **主要矛盾**：工程治理（SHA/指纹/回执）非常严格，但缺少版本控制、主训练函数过大、资产与日志高度冗余、真机窗口昂贵；因此**“降低每次人工闭环的浪费”比“增加更多实验”更重要**。
6. **简化方向（新增）**：取消 RUN_ID、operator receipt、release manifest 等跨文件同步机制，改为**单机独立运行 + git 管理**；每次运行只保留一个自动生成的运行目录与 `run_meta`（git commit、配置快照、设备、时间）。
7. **迁移方向（新增）**：当前控制合同、数据工件与 Bladed 工程仍绑定 15 MW；迁移到 22 MW 需要引入 **TurbineProfile** 并把常量/工件按机型拆分，**不能只改额定功率**。

- 训练队列在历史诊断中完整完成（4/4 轮、92/92 case、无跳过/重试）。

- 不能声称策略已通过电量/载荷验收。

### 3.2 P0 风险

#### R-01 工作区无版本控制，资产不可回溯

- **证据**：`git status` 报“不是 git 仓库”；无 `.git`、`.gitignore`；工作区 106 GB，`RL/experiments` 84 GB。
- **影响**：无法 `bisect`、无法回滚、无法用提交号绑定“某次运行对应哪版源码”；现有 SHA/manifest 只能证明“文件字节”，不能替代历史。
- **缓解**：`git init` + `.gitignore`（排除实验产物与大数据），大文件用 LFS 或外部存储；为 R2 打基线 tag；保留现有目录不删除。
- **验收**：`git log` 可见基线；`git status` 干净；大目录被忽略。

#### R-02 训练主链巨型函数，回归风险高

- **证据**：`run_queue_training` 2178 行（[train_rl.py:1310](../RL/train_rl.py#L1310)，AST 实测）；`train_rl.py` 4615 行；推理侧 `run_inference` 921 行（[run_bladed_inference.py:734](../RL/infer/run_bladed_inference.py#L734)）。
- **影响**：修改 reward、队列、日志、检查点都需在巨函数内定位；难以做单元隔离与行为对比。
- **缓解**：按“行为保持”原则拆分（`QueueRunner` / `TrainingLoop` / `MetricsSink` / `CheckpointManager`），先补黄金测试再动刀；不与实验改动同批进行。
- **验收**：固定 replay 批次上的指标逐项一致；全量离线测试通过；diff 不含语义变化。

#### R-03 物理目标未达，学习信号受限

- **证据**：历史诊断 ΔE = −0.712%，三叶根峰值 +4.07%/+4.78%/+5.02%；探索噪声全为 0（[配置:253](../RL/configs/WT15_STATE20_RL_20261023_R2/state20_physical_23wind_round600_training.json#L253)、[:452](../RL/configs/WT15_STATE20_RL_20261023_R2/state20_physical_23wind_round600_training.json#L452)）；replay 过滤 fallback 转移。
- **影响**：当前 Actor 更接近“BC 保守微调”，数据分布窄；继续跑同配置的 23×4 很可能重复同一失败结构。
- **缓解**：先做最差风况归因（10–12 电量、14/15/18 峰值、3/4 低速恢复），再做受控探索/BC 权重消融；一次只改一个因素，用固定 checkpoint 评估。
- **验收**：4×4 上先验证改动方向；23×4 上按预注册口径比较 ΔE/ΔL；不以 reward 曲线代替验收。

#### R-04 人工闭环窗口昂贵且不可自动化

- **证据**：Bladed 在 Windows；每个 slot 需人工加载工程/风文件并跑满 600 s（[训练操作笔记:283](./训练操作笔记.md#L283)）；4×4 为 16 次、23×4 为 92 次。
- **影响**：每次运行占用人工时间；准备不足、清单遗漏或中途异常都会浪费整批。
- **缓解**：**不做自动化加载**；改为“4×4 先试错 + 运行前预检 + 运行中逐 slot 清单 + 运行后 Linux 后处理一次到位”。
- **验收**：单批因准备问题导致的 abort 为 0；每个 slot 的 END/身份/计数均有记录。

#### R-05 运行资源不足以稳定支撑 23×4

- **证据**：30 GB 内存（采样时可用约 10 GB）；GPU 不可用；18 GiB 影子记录预算（R2 `max_total_bytes=19,327,352,832`）；84 GB 历史实验占盘。
- **影响**：23×4 可能在启动或运行中因内存/磁盘失败；GPU 缺失使训练与评估退化到 CPU。
- **缓解**：清理/外置历史实验；恢复 GPU 或明确 CPU 预算；运行前做资源 preflight 并留余量；继续使用 `compact_streaming` 日志。
- **验收**：preflight 资源检查 PASS 且有明确余量；单批运行 RSS/磁盘峰值低于预算。

### 3.4 P2 风险

#### R-12 影子异常静默，缺少可观测性

- **证据**：[physical_load_shadow.py:803](../RL/utils/physical_load_shadow.py#L803) 使用 `except Exception: shadow.submission_failed()`，按设计不阻断控制。
- **影响**：若 worker/记录异常持续发生，载荷诊断会静默缺失，事后才发现。
- **缓解**：在运行 summary 中显式输出 `submission_failed`/`completed`/`unknown` 计数与阈值告警；离线评价器校验计数闭合。
- **验收**：summary 含影子健康字段；异常计数超阈值时运行标记为 degraded。

#### R-13 Q-health gate 双配置语义

- **证据**：配置同时存在 `actor_q_health_gate.enabled=true` 与 `actor_optimizer_health_gate`；代码在 optimizer gate 存在时不实例化前者（[train_rl.py](../RL/train_rl.py#L1365) 附近）。
- **影响**：读者可能误以为趋势型 Actor-Q gate 正在运行。
- **缓解**：配置校验中显式声明互斥/优先级；文档标注“当前实际生效的是 optimizer gate”。
- **验收**：歧义配置被拒绝或给出明确告警；运行日志打印实际 gate 类型。

#### R-14 通信默认值硬编码（已验证，说明项）

- **证据**：[udp_python-DLC1.3-new.py:21](../bladed_env/udp_python-DLC1.3-new.py#L21) 默认 `192.168.56.1:8888`；该地址与端口已由使用者确认通信正常。
- **影响**：可移植性一般，但当前环境稳定，不构成缺陷。
- **缓解**：文档登记为“已验证环境约定”；如需迁移，使用现有 `env.udp_host`/`env.udp_port` 配置覆盖，不改 DLL 语义。
- **验收**：环境说明中有一处权威记录；不引入行为变化。

#### R-15 大工件与双份队列循环

- **证据**：84 MB 的 paired PID 参考 JSON；训练侧 2178 行队列逻辑与推理侧 921 行各自维护。
- **影响**：加载成本、逻辑漂移。
- **缓解**：短期只做文档与加载基准；中期在 M2 之后评估统一队列循环；大 JSON 转换列为可选、需兼容性验证。
- **验收**：任何格式变更都不破坏现有 SHA/loader；训练/推理共用同一份队列状态机。

### 3.5 P3 风险

#### R-16 4×4 / 23×4 场景标签可发现性

- **证据**：4×4 流程在 [训练操作笔记](./训练操作笔记.md#L249)（`smoke_4x4`、16 slot），23×4 流程在 [从原始PID数据重建state20训练链](./从原始PID数据重建state20训练链.md#L419)（`full`、92 slot）；两文均未在首屏显式标注场景。
- **影响**：读者可能用 23×4 的预期执行 4×4 步骤，或反之。
- **缓解**：两文首屏各加一句场景说明与互链；保留两条流程，不删除、不合并。
- **验收**：任一操作文档在前 10 行内能看出对应 4×4 还是 23×4。

### 3.6 P1 风险（本轮新增）

#### R-17 RUN_ID/回执/发布清单耦合过重，与单机独立运行不匹配

- **证据**：`RUN_ID` 在 `RL/*.py` 中 36 处、19 个文件；文档中约 100 处；12 个 `*receipt*.json`；2 个 `release_manifest.json`；launch/identity 相关模块合计约 2,980 行（[physical_load_shadow_launch.py](../RL/utils/physical_load_shadow_launch.py) 940 行、[queue_case_identity.py](../RL/utils/queue_case_identity.py) 675 行、[release_manifest.py](../RL/utils/release_manifest.py) 470 行等）；Windows DLL 还依赖 `BLADED_RL_MANUAL_BATCH_RUN_ID`、`BLADED_RL_QUEUE_EPOCH`、`BLADED_RL_CONDITION_INSTANCE_ID`（[controller.cpp:80](../bladed_env/udptest/udptest/controller.cpp#L80) 附近）。
- **影响**：每次运行要新建配置目录、生成 receipt、绑定 runtime identity、同步 Windows 状态；单机场景下这些步骤只增加失败面，不增加安全性。一次身份不符或 receipt 失效就会中止整批。
- **缓解**：分两步——**过渡期**仍沿用现有 RUN_ID 流程，避免改造中失去追溯；**目标态**改为 `runs/<UTC时间戳>_<git短SHA>/` + `run_meta.json`，删除 receipt/attestation/release manifest，只保留启动时的最小兼容校验。详见第 9 节。
- **验收**：启动不再要求 RUN_ID/receipt；`run_meta.json` 含 git commit、dirty 标记、配置快照、设备与起止时间；4×4 可完整跑通。

#### R-18 15 MW 硬编码与数据耦合，22 MW 迁移需大范围拆分

- **证据**：38 个配置 JSON 含 `15MW`/`WT15` 标记；动作合同常量写死在 [control_contract.py:18](../RL/utils/control_contract.py#L18)（`21_586_451.33303 Nm`、`0.43 rad`）；额定功率、齿比、动作边界、速率、奖励参考分散在 config 的 `env`/`control`/`reward`；B4、state/action envelope、S2/U1 标定、paired PID 参考、BC 数据集与 checkpoint、physical shadow bundle 均按 15 MW 数据拟合；Bladed 工程为 `bladed_env/15MW_rl.prj`；原始 PID 数据为 15 MW 的 23 条轨迹。DLL（[controller.cpp](../bladed_env/udptest/udptest/controller.cpp)）未发现 15 MW 常量，可复用。
- **影响**：换 22 MW 时只改 `rated_power` 会产生“参数是 22 MW、模型/参考仍是 15 MW”的静默错配；B4/BC/envelope/shadow 不能按比例缩放，必须重建。
- **缓解**：引入 `TurbineProfile`（机型参数）+ 按机型分目录的资产根；把 `control_contract.py`、离线工具、测试中的常量外置；22 MW 重建数据与工件后再跑 4×4。详见第 9 节。
- **验收**：核心代码不再包含 15 MW 专用常量；15 MW 与 22 MW 各自用独立 profile/资产目录；两者都能通过同一套 preflight 与 4×4 验证。

### 4.4 实验计划（依赖人工窗口）

13. **先 4×4**：用 16 slot 验证合同、日志、资源、END 收尾与身份；不产出正式性能结论。

## 5. 修改计划

### 5.1 原则与门禁

- **不改冻结语义**：state20 观测、B4、BC v3、安全包络、动作边界、控制指纹在未升版前不得改动。
- **过渡期沿用现有流程**：S1（去 RUN_ID）完成并验证前，仍按现有 RUN_ID/receipt 运行，避免改造中失去追溯。
- **目标态用 git + 自动运行目录**：S1 完成后，以 `runs/<UTC时间戳>_<git短SHA>/` 记录每次运行；不再要求跨文件 receipt/同步。
- **保留最小兼容校验**：数据 schema、观测维度、动作边界、checkpoint/工件版本仍需启动时校验；删除的是“仪式”，不是“防错”。
- **先 4×4 后 23×4**：4×4 是进入 23×4 的前置条件，不是验收。
- **重构与实验分开**：同一批不同时做“改代码 + 跑闭环”。
- **Linux/Windows 分工**：Linux 做离线校验、测试、后处理；Windows 只做人工闭环与运行期证据采集。

- `conda run -n wind python -m unittest discover -s RL/tests -p 'test_*.py' -q` 全绿（Fake UDP/离线 fixture）。

- 指标按 [控制策略指标_更新版](./控制策略指标_更新版.md) 计算并分级汇报。

**简化/迁移（M6/M7）**

- 启动不再要求 RUN_ID/receipt；`run_meta.json` 含 git commit、dirty 标记、配置快照、设备与起止时间。

- Windows DLL 环境变量简化后，4×4 通信与排程验证通过。

### 5.5 回滚策略

- 每个 M 阶段独立分支/提交，失败 `git revert`；不混合阶段。
- 运行批次只增不改：旧运行目录、历史 receipt 永久保留；M6 后新运行不再生成 receipt。
- 配置变更不覆盖旧文件；新运行目录 + `run_meta`；必要时保留旧 DLL/旧工程副本。
- 影子/日志异常时优先降级为“不可评估”，不伪造记录。

## 9. 架构简化与多机型迁移计划（新增）

> 本节回应两项新要求：**取消 RUN_ID 绑定与复杂本地版本管理**、**从 15 MW 拆分以支持 22 MW**。原则是“删仪式、留防错”：去掉跨文件同步与授权回执，但保留数据 schema、观测维度、动作边界、checkpoint/工件版本等最小兼容校验。

### 9.1 去 RUN_ID 与本地版本管理简化

#### 9.1.1 现状与处置

| 机制 | 当前位置/作用 | 处置 |
|---|---|---|
| RUN_ID | `experiment_name`、`RL/configs/<RUN_ID>/`、`RL/experiments/<RUN_ID>/` | **替换**为 `runs/<UTC时间戳>_<git短SHA>/` |
| operator receipt / attestation | 启动前声明工程/DLL/seed/身份一致 | **删除**（S1 后不再生成） |
| runtime identity / pinned SHA | 绑定配置、源码、DLL、工程、回执 | **替换**为 `run_meta.json` 自动记录 |
| release manifest / profile report | 跨组件 SHA 清单与发布身份 | **归档**，以 git tag 取代 |
| Windows `RUN_ID`/`QUEUE_EPOCH`/`CONDITION_INSTANCE_ID` | DLL 手工队列状态与身份 | **简化**为自动序号或移除（需重建 DLL） |
| strict case identity（全 trace SHA） | 匹配 Bladed 轨迹与 PID 参考 | **简化**为 frame/time/condition 校验 |
| control fingerprint / artifact SHA | 防止 B4/BC/state20 工件混用 | **保留最小集**（一个组合哈希） |
| schema version（数据/观测/动作） | 兼容性校验 | **保留** |
| `dependencies.json` | 依赖清单回执 | **删除**，由 lock 文件 + git 取代 |
| `append_timestamp=False` | 强制 RUN_ID 目录 | **恢复时间戳目录** |

盘点规模：`RUN_ID` 在 Python 中 36 处/19 个文件、文档中约 100 处、12 个 receipt JSON、2 个 release manifest；launch/identity 相关模块约 2,980 行。**这是一次跨 19 个文件的重构，不是改几个字符串。**

#### 9.1.2 目标运行布局

```text
runs/
  20261102T091500Z_a1b2c3d/
    config.json          # 本次生效配置快照
    run_meta.json        # git commit/dirty、设备、起止时间、工件哈希
    metrics...           # compact 日志与 summary
```

`run_meta.json` 至少包含：

- `git_commit`、`git_dirty`、`git_diff_stat`；
- 配置路径与配置快照 SHA；
- 设备（CPU/GPU）、开始/结束时间；
- 关键工件哈希（B4、BC、envelope、paired reference、shadow bundle）；
- 运行模式（4×4 / 23×4、online/offline、baseline/actor）。

#### 9.1.3 启动时保留的最小校验

1. 数据 schema 与观测维度（state20 = 20）。
2. 动作边界/速率与当前 profile 一致。
3. checkpoint 与 B4/envelope 的兼容哈希（一个组合哈希，不再逐文件回执）。
4. `git_dirty=true` 时给出警告（不阻断，但写入 `run_meta`）。
5. 启动 Bladed 前需要一次显式确认（命令行 `--confirm-run` 或交互 y/N）。

#### 9.1.4 S1 实施步骤

1. 新增 `RL/run_meta.py`：生成运行目录、写 `run_meta.json`。
2. 替换 19 个文件中的 RUN_ID 用途（配置目录、实验目录、日志字段）。
3. 归档 `prepare_physical_operator_run.py`、`finalize_physical_operator_run.py`、`release_manifest.py`、`build_unified_profile_release_manifest.py`。
4. 缩减 `physical_load_shadow_launch.py` 的 receipt/runtime identity 校验，保留资源与模式校验。
5. 简化 DLL 环境变量（与 DLL 重建同批）；先保留 `BLADED_RL_MANUAL_BATCH_PROFILE`/`ROUNDS`。
6. 更新测试与文档；旧 receipt/运行目录只归档、不删除。

**验收**：无需 RUN_ID 输入即可完成 4×4；`run_meta.json` 可定位到 git commit；没有 receipt 相关阻断。
