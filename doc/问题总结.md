# 23 风况控制策略问题分析与修正路线

更新时间：2026-09-25

## 0. 先看结论（通俗版）

本文讨论的不是重新设计整台风机，而是在当前 Bladed、UDP、B4 residual 和 TD3+BC 框架内，先让策略在已有的 23 个物理风况上不把叶根极限载荷推得高于 PID，再在这个约束内寻找发电量改善。

### 当前状态摘要

1. **训练产物完整，训练稳定性问题已显著缓解。** state20 23×4×600 diagnostic run 完成 4/4 轮、92/92 个 condition、2,759,788 步、68,994 次 Critic update 和 16,603 次实际 Actor update；无跳过/重试、无 Critic Q hard guard 或 degraded。第 4 轮仍有 5,560 次 Actor update。VS Code 此后异常退出不能据此认定本次训练中断，也不能仅凭退出码 132 归因于训练或日志。
2. **旧实验的 gate-blocked fallback 级联已不再出现。** 旧实验的 689,936 个 Q-health blocked fallback step 在 state20 中降为 0 个 policy-blocked Q-health fallback；state20 总 fallback 为 93,269 步、3.38%，主要来自启动/停机和低速 recovery，而不是 Actor gate 关闭。
3. **PID 对照已升级为 state20 paired reference。** 参考工件按 `condition_id + PID raw CSV SHA-256 + exact [0,600] s window` 绑定功率和三片 My；`condition_instance_id` 属于在线队列身份，不是 PID reference 的查找键。另有独立的 $180\ \mathrm{s}$ 参考，不能混用。
4. **训练诊断结果未达到电量—载荷目标，但不是正式验收报告。** 92 条轨迹的电量先求和再比较为 $\Delta E=-0.712\%$；三片叶根分别按“RL 平均峰值 / PID 平均峰值”计算，峰值增加 $4.07\%/4.78\%/5.02\%$，对应平均降低率约 $-4.63\%$。第 4 轮相对第 1 轮未见持续改善。
5. **历史结果仍是 non-release diagnostic。** 2026-09-19 训练 run 仅验证 prefix case identity，逐工况训练电量按每步 $P\Delta t$ 累加，不能充当正式梯形积分验收。2026-09-25 曾完成离线 W5/W6 软件推进；后续统一发行中不再提供 NN 载荷 checkpoint/profile。strict inference identity、multi-scenario evaluator 和 hash-bound release manifest 代码仍保留；但尚无冻结策略真实 Bladed full-trace 验收、真实 RL `zoh_candidate` 覆盖或独立 guard calibration。因此仍没有正式策略验收或 V1 许可。

### 已完成的修正

1. 使用 state20/v3 action、observation、B4、BC 和 resolved contract fingerprint，阻止旧 obs12/v1、v2 工件混用。
2. 将 state20 torque request high 统一为 $21,586,451.33303\ \mathrm{Nm}$；$21\ \mathrm{MNm}$ 保留为实际 `I_ElectricalTorque` 反馈边界，$22\ \mathrm{MNm}$ 只用于接口余量诊断。
3. 保留 `agent.max_target_q_abs_mean=20` 的 Critic 硬 Q guard，增加独立 `actor_optimizer_health_gate`；它只冻结 Actor optimizer update，不自动剥夺有效 Actor action 的执行权。配置中仍有阈值为 20 的趋势型 `actor_q_health_gate`，但本次启用 optimizer gate 时**该趋势 gate 未实例化**；不能将两者或 200 次启动恢复期的 blocked update 混为“Q 超限”。
4. 引入 `train.execution_replay_contract`，按 Actor、baseline、rollback、low-speed recovery 区分 replay source，避免把不同原因的 fallback 混成一种失败。
5. 本次 state20 queue 使用 `legacy_long_form`，保留逐 step、逐 update、逐 condition 和逐 checkpoint 的记录，便于追溯；代价是实验目录约 $81\ \mathrm{GB}$，其中总指标表和逐步指标表分别约 $40.8/40.6\ \mathrm{GB}$，不宜直接在编辑器中打开或整表读入内存。

### 仍在推进的目标

1. 已有 below-rated、transition、above-rated 的**软**状态条件化 reward 和逐轮双约束；下一步是让逐工况电量/逐叶根峰值的优化和正式验收更一致，而非重新增加一套同名权重。
2. 三片 My 峰值、剩余 headroom 曾探索 PID-only NN shadow/pending 方案；该 NN 候选不属于当前统一发行。当前仅运行 `physical_fir_v2` 只读 shadow；任何未来 NN 风险监督均需新批准方案、新权重和独立校准。
3. 排查风况 10--12 的功率缺口、14/15/18 的超峰以及 3/4 的低速恢复；量化 recovery 在 Critic batch 中的真实采样比例，避免仅凭存量占比判断训练影响。

### 这套方案不承诺什么

- 当前系统尚不能保证“绝不超过 PID 峰值”。共享 predictor interface/dataset 合同仍存在，但当前没有活动 NN 权重，也没有真实 RL 独立 coverage/calibration 证据。当前物理 FIR profile 是发送后只读 shadow，不能宣称已经有动作前载荷保护。
- 当前不以手动制造多种外部扰动为前提；先在已有 raw 对应的固定 case 上把对照、约束和训练链路做正确。
- 最终是否通过，仍严格由 [控制策略指标_更新版.md](控制策略指标_更新版.md) 的累计电量与三片叶根极限 My 口径判定，而不是由训练 reward、预测器误差或 smoke 是否完成决定。

- 最终验收合同 [控制策略指标_更新版.md](控制策略指标_更新版.md)：同工况、同时间窗下的累计电量相对 PID 改善和三片叶根 My 极限载荷平均降低。
- 2026-09-24 复核仅从约 $251\ \mathrm{kB}$ 的逐工况指标、流式扫描的约 $181\ \mathrm{MB}$ 更新指标、各轮小型 checkpoint 和约 9 万条独立 BC validation 样本取数；未把约 $81\ \mathrm{GB}$ 的训练长表一次读入内存。训练性能表覆盖整个 $[0,600]\ \mathrm{s}$，不应用下述 raw 稳态 $t\geq60\ \mathrm{s}$ 过滤规则重新解释。

除非另行说明，raw 统计使用 $t\geq60\ \mathrm{s}$ 的样本，以避免把每个独立 case 的初始瞬态误作稳态规律。这个筛选不删除真实的启动/停机状态；启动和停机仍单独由状态机统计。

本节给出后续判断所依赖的证据和技术结论：

1. state20 已使用 paired PID power/load reference 和 state-conditioned reward contract，但核心权重仍不是最终“电量-极限载荷”验收本身；下一步仍需按运行状态切换约束，而不只是继续调一组全局 reward weight。
2. 不应把风速简单替换成转速。额定以上转速被控制在近似常数，无法代替风速预测桨距；额定以下转速是很强的闭环反馈。正确方案是：风速作为滤波后的前瞻量，转速、实际功率和实际电磁转矩作为闭环量，联合判定运行状态和动作包络。
3. state20 已把 PID demand/action envelope 提升到 $21.58645133303\ \mathrm{MNm}$；旧 legacy 路线仍保留 $21.0\ \mathrm{MNm}$ 截断，不能与 state20 工件混用。实际 `I_ElectricalTorque` 仍是执行反馈边界。
4. 旧实验第四轮的大量 fallback 已定位为 Actor Q-health gate、控制执行和 replay filter 的耦合级联；state20 通过独立 optimizer gate 和 execution-mode replay 显著缓解。当前配置的趋势型 Actor Q-health gate 未运行，剩余 fallback 主要属于启动/停机和低速恢复。
5. 当前重点从“修复 Actor 中断”转为“诊断功率损失和峰值恶化、审计 recovery 采样、校准载荷风险”；现有上游 state20 工件已生成，后续仍需 strict identity 的冻结策略评估和发布前置产物。

## 2. raw 数据揭示的真实运行规律

### 2.1 功率、转矩和转速的物理关系

对于同一根高速轴上的实际电磁转矩 $T_e$ 与发电机角速度 $\omega_g$，电功率近似满足：

$$
P_e\approx \eta T_e\omega_g
$$

其中 $T_e$ 的单位为 Nm，$\omega_g$ 的单位为 rad/s，乘积单位为 W，$\eta$ 为发电机效率。验证这个功率关系时必须使用实际通道 `I_ElectricalTorque`，而不是 demand label `O_PcsTorqueDemand`；后者可能已被执行器、电气模型或其他保护环节截断。这只说明功率/载荷响应应使用实际转矩建模，不表示 `I_ElectricalTorque` 应替代 Actor 的 demand action 范围。

raw 的稳态样本验证了这一点：

| 检查 | 结果 |
|---|---:|
| `corr(I_RealPower, I_ElectricalTorque * I_GeneratorSpeed)` | $1.000000$ |
| $I_\mathrm{RealPower}/(I_\mathrm{ElectricalTorque}\cdot I_\mathrm{GeneratorSpeed})$ 的 $p05/p50/p95$ | $0.930000/0.930000/0.930000$ |
| `corr(I_RealPower, O_PcsTorqueDemand * I_GeneratorSpeed)` | $0.999898$ |
| 上述命令估计比值的 $p05/p50/p95$ | $0.922056/0.929863/0.932331$ |

工程文件中的 `VS_GenEff=93%` 与该比例一致。`I_ElectricalTorque` 和 `I_GeneratorSpeed` 在这份 UDP 数据里是同一侧、同一量纲的信号；若日后改用低速轴转矩，必须按齿轮箱比换算，不能直接复用此乘积关系。

下表按测得风速划分，仅用于展示分布；实际运行状态不能只由单一风速阈值决定。

由此可见：

- 额定以下不是一个“固定零桨距”区域。3--6 m/s 含大量启动、停机或低功率样本；7--10 m/s 才逐步体现常规 MPPT 转矩上升和接近 $0$ rad 的桨距。

## 3. 风速还是转速：结论是“联合使用”，不是替换

### 3.1 数据判据

在额定以下：

| 目标 | 与风速相关系数 | 与转速相关系数 |
|---|---:|---:|
| `O_PcsTorqueDemand` | $0.92536$ | $0.93846$ |
| `O_PitchPositionDemand1` | $-0.46029$ | $-0.23807$ |

在额定以上：

| 目标 | 与风速相关系数 | 与转速相关系数 |
|---|---:|---:|
| `O_PcsTorqueDemand` | $-0.14077$ | $-0.97020$ |
| `O_PitchPositionDemand1` | $0.88497$ | $0.06711$ |

额定以上用简单线性模型预测 PID 桨距时，风速的 $R^2=0.7832$、MAE=$0.02787$ rad；仅用转速的 $R^2=0.0045$、MAE=$0.06406$ rad。原因不是转速无用，而是额定以上控制器刻意把它稳定在额定值附近，转速本身不再携带足够的来流变化信息。

因此，以下两种极端做法都不正确：

- 错误：只按风速分区，把转速、功率和桨距只当普通输入，忽略它们对实际运行状态的确认作用。
- 错误：完全删除风速、只按转速分区。这样会失去额定以上桨距调节最强的前瞻信号，也会在转速被调速器锁定时无法区分 15 m/s 和 25 m/s 的气动载荷环境。

### 3.2 现有状态机与改进方向

state20 已通过 `state_calibration_v1` 记录因果风速滤波、风速区域迟滞及确认时长，并结合转速、实际功率和持续时间识别启动/运行/停机与负功率异常；观测已包含状态 one-hot 和区域 one-hot。下一步不是从零建立状态机，而是审计这些信号在风况 10--15 的边界切换、低速恢复和功率/载荷峰值窗口中是否正确驱动 residual 准入。建议继续保持以下信号分工：

| 信号类别 | 信号 | 职责 |
|---|---|---|
| 前瞻调度 | 因果滤波后的风速/风速估计器输出、其可信度和变化率 | 预判来流与桨距需求，特别是额定以上 |
| 闭环功率 | `I_RealPower`、`I_ElectricalTorque`、`I_GeneratorSpeed` | 判断功率是否已接近额定、命令是否被执行器截断 |
| 闭环机械状态 | `I_RotorSpeed`、转速变化率、桨距位置和上一实际发送动作 | 判断调速误差、启动/停机、动作可行性与速率限制 |
| 载荷反馈 | 三片 `Blade root * My`、机舱加速度 | 载荷约束、在线保护和最终验收记录 |

现有状态机已经按“因果滤波风速决定区域候选，转速、真实功率和持续时间确认运行状态”实现第一版；实际桨距和上一发送动作保留为连续控制/包络输入。阈值已在 `state_calibration_v1` 中版本化，`raw_infer` 仅用于离线状态覆盖与抖动检查。改进前应先按既有阈值复现误分区/频繁切换案例，任何修改均需产生新合同版本、重建相关工件和 checkpoint，不得在验证中临时调整。当前阈值与状态码见 [开发执行计划.md](开发执行计划.md)。

现实中的风速传感器确实可能有延迟、偏差、机舱尾流影响或短时噪声，但当前 raw 是仿真数据，不能据此量化真实现场风速误差。部署前应增加风速延迟/噪声/缺失的鲁棒性测试，必要时退化为以转速、功率、桨距为主的反馈控制，而不是永久删除风速。

当前 B4 并非只输入风速。它已经使用：

```text
filtered_wind_speed_mps
rotor_speed_rad_s
generator_speed_rad_s
real_power_w
previous_torque_nm
previous_pitch_rad
```

问题在于当前 `OperatingStateClassifier` 的 control region 切换仍主要由滤波风速的 $11.8/13.8$ m/s 阈值决定，尚需检查转速、实际功率、状态持续时间与 residual 准入的一致性。state20 已区分 `negative_power_abnormal` 与 `startup_stopped`，并给 Actor/Critic 加入状态编码；下一步是在版本化校准和闭环验证中改进多信号确认，不能把已有区分当成待实现功能。

## 4. 现有状态条件奖励与最终验收的差距

### 4.1 当前 reward 的缺口

本次 state20 diagnostic 的全局基系数为：

```text
power_weight = 1.0
blade_root_weight = 1.0
persistent_power_deficit_weight = 0.1
power_floor_weight = 0.0
```

**它们并不是在每个状态下同权生效。** `reward.state_conditioning.weights` 已将 `startup_stopped`/`negative_power_abnormal` 的优化权重设为零；对 below-rated、transition、above-rated 的功率乘数分别为 $1/0.75/0.5$，峰值载荷乘数分别为 $0.5/0.75/1$，并对持续功率缺口、连续超峰和动作连续性分别设状态乘数。当前 reward 包含 `relative_pid_energy`、逐叶根 `my_peak_increment`、超峰后的 `pid_excess` 和持续功率缺口项；旧转速偏差/变化/持续低速项及独立负功率惩罚已删除。`dual_constraint` 在每个完整 condition 统计三叶根超峰与电量不足，按完整 condition 的均值在轮末更新乘子。它们是**软奖励/惩罚与下一轮参数更新**，不是“逐片叶根不超 PID”或“电量不低于 PID”的动作前硬约束。低速保护与负功率异常回退/停止仍由执行层独立处理。

尚未解决的是：

1. 状态乘数已生效，但它们与 BC 约束、Critic 采样比例和最终同窗 $\Delta E/\Delta L_j$ 的量纲/权衡尚未验证；不可再把“尚未做状态条件化”列为当前故障。
2. `power_floor_weight=0`，持续缺口和双约束都是软项；本次风况 10--12 仍出现显著累计电量损失，不能宣称电量下界已得到保证。
3. `my_peak_increment` 仅在累计峰值首次超过 PID 时提供增量信号，超峰之后的 `pid_excess` 才持续惩罚；Actor 的 20 维 observation 未含三片 My、累计峰值或余量，无法在峰值发生前直接依据该风险作决策。本次风况 14/15/18 的峰值超额仍很明显。
4. 当前 condition 电量统计以每步参考功率及实际功率乘 $\Delta t$ 累加，不能直接当作正式同窗梯形积分；condition 双约束已记录终端超额并在轮末更新 $\lambda$，但尚未把“某片峰值即将超标”转换为经过独立校准的发送前保护。

所以，不能以“总 reward 上升”替代 [控制策略指标_更新版.md](控制策略指标_更新版.md) 的通过判定。

### 4.2 推荐的分区约束优化合同

对每个 case $c$，始终使用 PID 对齐轨迹作为参考，评估时按最终文档的梯形积分计算 $\Delta E_c$，按三片叶根分别计算 $\Delta L_{j,c}$；训练用的逐步可加代理量要单独标注。状态 $s_t$ 取启动/停机、额定以下、过渡、额定以上之一，异常负功率状态不参与 residual 优化。以下是**在现有 state20 软条件奖励与双约束基础上的下一步目标**，不是称当前代码完全没有这些机制。

额定以下的主目标应为：

$$
\max_\pi\ \Delta E_c
\quad\text{subject to}\quad
\Delta L_{j,c}\geq-\epsilon_L,
\quad j\in\{1,2,3\}.
$$

额定以上的主目标应为：

$$
\max_\pi\ \Delta L_c
\quad\text{subject to}\quad
\Delta E_c\geq-\epsilon_E.
$$

过渡区不宜追求单一极端，应同时保持功率、转速、桨距和载荷连续：

$$
\max_\pi\
w_E\Delta E_c+w_L\Delta L_c
-w_\omega\,\mathcal{P}_{\omega,c}
-w_a\,\mathcal{P}_{\Delta a,c},
$$

其中权重与容差必须在 holdout 和闭环实验前冻结，不能按最终结果反调。启动/停机状态不训练探索 residual，使用 B4/PID 恢复路径并排除出性能优化样本。

在线训练的可加 surrogate 应与最终指标对齐：

- 能量项以相对 PID 功率差乘实际 $\Delta t$ 作逐步代理，并在正式评估中使用完整对齐轨迹的梯形积分；额定以上对持续低于 PID 的功率缺口设置经事前冻结的目标，不能把软惩罚称为硬下界。
- 现有逐片累计 $\max|M_{y,j}|$ 和完整 condition 的 $g_j$ 已存在；下一步验证超峰惩罚是否及时、是否能在下一次相同 condition 改善，并在经过校准后增加发送前风险限制，不能把轮末更新乘子当成对当前超峰的补救。
- 额定以下优先奖励功率改善，但任何一片叶根出现持续或终端超限时提高约束乘子；额定以上优先降低载荷，但功率低于 PID 的容差后立即提高功率缺口惩罚。
- 最终验收仍按文档的三叶根平均 $\Delta L$ 计算；训练中建议同时守住每片叶根，避免一片恶化被另外两片的平均改善掩盖。

这不是要求三套完全独立的 Actor。当前已有共享 Actor/Critic、state20 状态编码和状态软动作包络；关键是将状态奖励、双约束、回放源分布与最终逐场景性能作因果消融。若共享 Critic 的尺度仍不稳定，再考虑独立 Critic head 或按状态归一化 value target，先不要直接提高 Q guard 阈值。

## 9. 通过同场景外部扰动约束极限 My 不超过 PID

状态：本节保留未来的逐叶根峰值保护路线，并区分已完成代码与未取得的物理证据。state20 已生成独立的 180/600 s paired PID reference、状态条件化 soft reward、逐 condition 超峰/缺电统计及轮末双约束。历史上有 interface v3 / dataset v2、候选 TCN、strict full-trace inference validator、多场景 evaluator 和 release manifest 代码；当前统一发行不包含 NN 权重。历史在线训练仍仅 prefix identity，尚无真实 strict-policy Bladed 轨迹、RL 动作分布独立 coverage/calibration 或动作前载荷保护授权。不能因为参考工件已配对、历史模型曾可加载或存在 shadow 字段就宣称策略已通过或预测器可干预。

### 9.1 `raw` 是当前可用的 PID 扰动基准

`bladed-data-new/raw/data_windspeed3.csv` 至 `data_windspeed25.csv` 不是固定风速下的静态标定表。每个文件都记录了对应名义风况下随时间变化的 `I_AverageWindSpeed`、功率、动作与三片叶根 My；用户已确认这些 PID 轨迹来自与训练相同的风速扰动场景。因此，当前 $23\times600\ \mathrm{s}$ 已使用由 raw 构建的 exact-window paired PID 对照，而不是即时风速插值曲线。**本次 prefix 验证尚不能证明整条 runtime 风轨与 PID 相同**，性能结论必须保留 diagnostic 限定。

对一个物理场景 $d$ 和一个 queue condition $c$，定义完整身份：

$$
s=(c,d,t_0,T),
$$

其中 $c$ 为 condition ID，$d$ 表示该 condition 已有的固定 Bladed 风况，$[t_0,T]$ 为实际比较时间窗。当前阶段不要求人工拆分或控制 $d$ 中的湍流、波浪、yaw、电网等分量；只要求 PID raw 与 RL 复用同一个既有 case。PID 与 RL 必须共享完全相同的 $s$。

这里必须分开记录 PID reference identity 与 runtime Bladed case identity。前者包含 `condition_id + raw path + raw SHA-256 + 时间窗`，后者包含 `condition_id + condition_instance_id + 固定仿真时间偏移 + canonical wind-trace signature`，并在可获得时加入 Bladed project/case fingerprint。仅匹配少量风速前缀只能说明 `prefix_matched`，不能证明完整 case 相同；只有完整 trace 或 case fingerprint 匹配时才能标记 `strict_case_matched` 并产生正式性能结论。该要求不增加人工外扰，只增强既有 case 对照的可追溯性。

从 PID raw 提取逐叶根极限载荷：

$$
L_{j,\mathrm{PID}}^{(s)}
=
\max_{t\in[t_0,T]}
\left|M_{y,j,\mathrm{PID}}^{(s)}(t)\right|,
\qquad j\in\{1,2,3\}.
$$

RL 在相同场景下产生：

$$
L_{j,\mathrm{RL}}^{(s)}
=
\max_{t\in[t_0,T]}
\left|M_{y,j,\mathrm{RL}}^{(s)}(t)\right|.
$$

如果工程要求是“每片叶根的极限 My 都不超过 PID”，则应增加独立于最终平均指标的逐叶根约束：

$$
L_{j,\mathrm{RL}}^{(s)}
\leq
L_{j,\mathrm{PID}}^{(s)}(1+\epsilon_j),
\qquad j\in\{1,2,3\}.
$$

$\epsilon_j$ 是在实验前冻结的物理载荷容差。若要求严格不超 PID，则取 $\epsilon_j=0$。浮点计算的舍入仅使用单独记录的 `comparison_tolerance_nm`，不得将其伪装成可事后放宽的物理载荷容差。这条逐叶根规则比 [控制策略指标_更新版.md](控制策略指标_更新版.md) 中“三个叶根降幅平均值”的 $L_0/L_1$ 更严格；报告必须分别给出 `strict_per_blade_pass` 和按官方公式计算的 `official_acceptance_pass`，不能用平均值掩盖单片叶根恶化。

### 9.2 只关心极限值，不把平均 My 设为目标

若目标是“允许平均载荷或普通时刻载荷高于 PID，但最终极限载荷不能高于 PID”，该目标的**验收口径**不采用 My 均值、RMS、p95 或逐时刻差值。当前 soft reward 除新超峰增量外，还保留超峰后的持续 `pid_excess` 惩罚，必须在训练分析中和“只计一次增量”的理想 shaping 分别列报。理想的逐片峰值超额为：

$$
g_j^{(s)}
=
\max\left(
\frac{L_{j,\mathrm{RL}}^{(s)}}
{L_{j,\mathrm{PID}}^{(s)}}-1,
0
\right).
$$

在线 shaping 可使用只在出现新超峰时非零的增量：

$$
\Delta g_{j,t}
=
\max\left(
\frac{\max(\widehat L_{j,t-1},|M_{y,j,t}|)}
{L_{j,\mathrm{PID}}^{(s)}}-1,
0
\right)
-g_{j,t-1},
$$

其中 $\widehat L_{j,t}$ 是 RL 到时刻 $t$ 为止的累计绝对峰值。单看该**增量项**，普通时刻的 My 即使高于对应 PID 瞬时值，只要没有创造超过 PID **整窗峰值**的新极限，就不会产生新的峰值惩罚；当前启用的 `pid_excess` 项则会在之前已超峰时持续非零，不能混淆两种代价。

当前 reward 的 `my_peak_increment` 已具备该机制的雏形：每个 condition 开始时清空三片叶根的累计峰值，记录 `reward_blade_root_*_peak_nm` 与 PID reference，并对新出现的 peak excess 计分。配置还启用了 `pid_excess`，使超峰后持续产生 soft penalty。当前 scalar 聚合使用 `blade_root_peak_aggregation=max`，即由最差的一片叶根主导 reward；它不直接惩罚 My 均值。

但当前机制仍不能保证不超 PID，原因如下：

1. 它是 TD3 reward shaping，而非动作发送前的硬可行性约束；峰值已经在执行后发生时，事后扣 reward 无法撤销该次超限。
2. state20 **已经**以 `condition_id + raw CSV SHA-256 + exact window` 绑定 PID 峰值，但本次在线只核验了前缀风速，没有 strict full-trace 的同扰动证据；不能将“reference 配对”误当成“runtime case 严格配对”。
3. 当前 20 维 Actor observation 不含三片 My、累计峰值或剩余余量，Actor 只能通过 Critic 的延迟回报间接学习风险。
4. state20 已分别生成 $[0,600]$ 与 $[0,180]\ \mathrm{s}$ 的 PID 参考；混用窗口仍会出错，但**本次 600 s 训练没有复用 180 s/旧按风速参考**。未来 smoke 必须选对应的 180 s 工件并核验哈希、身份与时间戳。

因此，$180\ \mathrm{s}$ smoke 应使用现有同一 raw 的 $[0,180]\ \mathrm{s}$ paired reference，$600\ \mathrm{s}$ full run 使用现有 $[0,600]\ \mathrm{s}$ 工件；若窗口从其他时间开始，则重新生成并冻结对应 $[t_0,T]$ 工件。不能用一个 $600\ \mathrm{s}$ 峰值表替代所有短窗口。

### 9.3 当前可行范围：复用既有物理风况，不手动注入新外扰

当前阶段不把手动控制多种外部扰动作为实现前提。现有 DLL 没有动态调用风速、湍流或风向增量 API；波浪、yaw 故障、电网故障和 External Loads Module 也未形成可由当前训练流程稳定复现的操作合同。要求人工逐项设置这些变量会降低可重复性，并使 PID/RL 对照难以归因。

现有 `bladed-data-new/raw/data_windspeed3.csv` 至 `data_windspeed25.csv` 已是当前可用的物理扰动基准：每条 PID 轨迹都包含对应训练 case 下随时间波动的风速、功率、动作和三片叶根 My。因此，当前可执行的方案只有一条：复用已经生成 raw 的 23 个 Bladed case，让 PID raw 与 RL 在相同 case 和相同时间窗内比较，不额外手动改变风、波浪、yaw、电网或外载荷。

当前 state20 paired PID reference 已按以下身份字段冻结：

```text
condition_id
PID raw CSV path + SHA-256
time_window_start_s + time_window_end_s
```

在线 case identity 还必须记录 queue `condition_instance_id`、固定仿真时间偏移和完整 `Time + I_AverageWindSpeed` trace signature；可取得时还应记录 Bladed project/case fingerprint。对 $23\times4\times600\ \mathrm{s}$，每个 RL slot 使用同一 `condition_id` 的已有完整 $[0,600]\ \mathrm{s}$ raw PID 对照；对 $180\ \mathrm{s}$ smoke，使用已生成的同源 $[0,180]\ \mathrm{s}$ PID 功率和三片 My 峰值。若 runtime identity 只能做到 reference 或前缀匹配，实验可作为训练/集成诊断，但不能声称是严格的同扰动 PID/RL 性能对照。

当前不实施以下项目：

- 不通过 `SetMeanFlowSpeedIncrement`、`SetTurbulenceIntensityIncrement` 或 `SetFlowDirectionIncrement` 动态注入扰动。
- 不要求人工配置新的波浪、yaw 故障、电网故障或 External Loads Module。
- 不把 active damper force、blade damper force 等控制/执行器接口伪装成外部环境噪声。

未来若需要泛化验证，优先增加一个预先生成、固定且可重复加载的 Bladed 风况，再先跑 PID、后跑 RL；这属于后续独立实验，不是修复当前峰值约束链的前置条件。

### 9.4 已有 paired PID reference 与尚缺的在线严格身份

旧的按名义风速压缩三叶根峰值的参考只用于历史实验。state20 paired PID power/load reference 工件仍保留：[600 s reference](../RL/data/paired_pid_power_load_reference_3_to_25_600s_v2.json) 和 [180 s reference](../RL/data/paired_pid_power_load_reference_3_to_25_180s_v2.json)。每条记录包含 `scenario_id`、`condition_id`、精确时间窗、PID raw CSV 路径及 SHA-256、精确时间戳、功率序列、三片 My 序列及绝对峰值，并保存可供严格 identity 校验的 canonical Time + I_AverageWindSpeed trace signature。训练功率/峰值参考从同一个 condition 的工件读取，而不是当前风速即时插值。`condition_instance_id` 用于在线 queue slot 身份审计，不作为 PID reference 查找键。旧 v2 诊断配置目录已清理。

剩余工作不是“再新增一份 600 s 峰值表”，而是用已实现的 strict validator/evaluator 在真实独立冻结策略推理中，核验每个 runtime condition instance 的固定偏移及整条 canonical 风轨，并绑定该次 run 的 identity sidecar、PID SHA 与完整窗口。历史 prefix identity 仍只验证少量前缀风速，不能追认全程同外扰；对 $180\ \mathrm{s}$ 与 $600\ \mathrm{s}$ 也不能共用同一峰值或验收结果。若历史 raw 没有 `.wnd` 文件 hash、湍流种子或波浪/yaw 配置，不得伪造这些元数据；未来新增 case 时先保证 PID 与 RL 都能加载同一冻结场景。

### 9.5 从 soft reward 到真实峰值保护

仅靠终端峰值 reward 不能在物理上保证不超阈值。应采用三层机制：

1. **独立载荷风险输入**：动作发送前，短时预测器读取当前三片 $|M_{y,j}|$、累计峰值比 $\widehat L_{j,t}/L_{j,\mathrm{PID}}^{(s)}$、剩余余量

	$$
	h_{j,t}=1-\frac{\widehat L_{j,t}}{L_{j,\mathrm{PID}}^{(s)}},
	$$

	以及运行状态、转速、功率、桨距和实际发送动作历史。预测器可独立读取 UDP payload，不必立刻扩大 Actor 现有的 **20 维** observation；这样不会在同一轮改动 Actor、BC dataset、normalization 和 checkpoint。待预测器与约束链稳定后，再评估是否将这些风险量显式加入 Actor。
2. **训练约束（已有软实现）**：state20 已对新超峰增量 shaping，并在完整 condition 结束时统计 $g_j^{(s)}$ 和电量不足，轮末更新拉格朗日乘子；它们影响后续 reward/训练，不会事后消除已发生的峰值。下一步应量化每片约束在下一轮是否真正降低超额，而不是再声称“当前尚无 dual constraint”。
3. **发送前安全监督器（未获授权）**：当前没有可加载的 NN 载荷候选或真实 RL 动作分布独立校准 artifact/coverage。统一发行使用物理 FIR 发送后只读 shadow，不得对候选 torque/pitch residual 做软/硬干预，也不能声称已具备 RL 有效预测覆盖或硬峰值保证。任何未来 NN 候选须重新训练、冻结并独立准入。详细限制见第 9.6 节。

平均 My 不应进入该三层机制的优化代价，但真实机组的绝对结构/安全限制、低转速保护、动作幅值和速率限制仍必须独立保留；“不约束平均 My”不等于允许破坏任何物理保护。

### 9.6 短时载荷预测器：同步训练、分阶段开启、逐级干预

**功能设计草案，非当前实现：** 共享 interface/dataset 合同及通用代码保留；当前工作区没有载荷 NN checkpoint。下文关于训练 NN、在线更新、calibration 和 `soft`/`hard` 的内容只描述未来若重新立项时可能采用的要求，不代表当前存在相应权重、运行配置或干预授权。当前统一发行只使用 `physical_fir_v2` 只读 shadow，soft/hard 仍未授权。

#### 9.6.1 它解决什么问题

短时载荷预测器不是第二个 Actor，也不替代 B4、PID 或 Bladed。它回答的是一个动作发送前的问题：给定当前真实状态和一组候选实际动作，未来很短的窗口内三片叶根的最大 $|My|$ 是否可能越过该 case 的 PID 峰值边界。

对预测窗口 $H$，建议同时训练 $H\in\{0.10,0.20,0.50\}\ \mathrm{s}$。令 $K_H$ 为对应的未来有效控制步数，预测目标使用相对 PID 的无量纲峰值：

$$
y_{j,t}^{(H)}=
\frac{
\max_{1\leq k\leq K_H}
\left|M_{y,j,t+k}\right|
}
{L_{j,\mathrm{PID}}^{(s)}},
\qquad j\in\{1,2,3\}.
$$

这样，不同风况和不同叶根的量级被同一个“是否接近或超过 $1$”的尺度对齐。raw 分析显示，许多峰值从最终峰值的 $95\%$ 到峰顶只有约 $0.08$--$0.18\ \mathrm{s}$；因此只预测下一帧或等 My 已超阈值才回退都不够，至少需要覆盖 $0.10$--$0.20\ \mathrm{s}$ 的风险窗口，并用 $0.50\ \mathrm{s}$ 窗口识别更早的趋势。

##### 建议框架：延迟感知的双阶段因果预测器

预测器不能把“Python 回传命令的时刻”和“该命令已改变叶根 My 的时刻”视为同一步。当前 UDP 时序为：Bladed 在仿真时刻 $t$ 发送测量帧，Python 根据该帧回传动作 $u_t$，DLL 在同一控制回调末尾设置新的 generator torque demand 和 collective pitch demand，随后 Bladed 在后续仿真步中经过电气、桨距执行器、气动和结构动力学产生新的 My。`udp_action_apply_lag_ms` 仅表示墙钟收包到发包延迟，不能代表风机物理响应延迟。

raw 与工程给出的是有效延迟的初始先验，而不是可永久写死的固定纯延迟：`O_PcsTorqueDemand` 对 `I_ElectricalTorque` 的逐文件最佳对齐约为 $4$ 帧，即 $0.08\ \mathrm{s}$；`O_PitchPositionDemand1` 对 `I_PitchPosition1` 的最佳对齐约为 $12$ 帧，即 $0.24\ \mathrm{s}$；电气系统还配置了 `timeConst=0.1\ \mathrm{s}$。桨距相关延迟应由历史和实际桨距反馈共同学习，不能只根据一个常数平移命令序列。

建议使用轻量的因果 TCN 或 NARX 型网络，而不是将单帧动作直接回归到下一帧 My。初版使用固定 $L=50$ 帧的历史窗口，即 $1\ \mathrm{s}$，以覆盖转矩、桨距和结构的短期记忆；所有卷积或递归状态只能读取当前及过去帧，不能看到未来 My 或未来真实风速。

```text
过去 1 s 的物理状态、My 与实际发送动作历史
	+ 当前候选 torque/pitch 动作及其短期续航计划
						 |
						 v
		  因果时间编码器（TCN / NARX）
						 |
		  +--------------+--------------+
		  |                             |
		  v                             v
实际执行状态预测头                 三叶根载荷预测头
(实际转矩、实际桨距)               (未来 My 轨迹、多窗口峰值)
		  |                             |
		  +------------->---------------+
						 |
						 v
			   保守的未来峰值上界
```

第一阶段显式预测执行器/电气状态：

$$
\widehat v_{t+1:t+K}
=f_{\mathrm{act}}
\left(x_{t-L+1:t},u^{\mathrm{sent}}_{t-L+1:t-1},U^{\mathrm{plan}}_{t:t+K-1}\right),
$$

其中 $v=(T_e,\beta)$ 是实际电磁转矩和实际集体桨距，$u^{\mathrm{sent}}$ 是已发送命令，$U^{\mathrm{plan}}$ 是候选命令的短期续航计划。第二阶段以预测的实际执行状态而不是裸 command 预测三片叶根响应：

$$
\widehat M_{y,1:3,t+1:t+K}
=f_{\mathrm{load}}
\left(x_{t-L+1:t},\widehat v_{t+1:t+K},U^{\mathrm{plan}}_{t:t+K-1}\right).
$$

两个预测头共享因果编码器，但分别输出实际转矩/桨距轨迹和三片 My 轨迹。实际执行状态是辅助监督任务：它迫使模型先学习“命令 $\rightarrow$ 执行器滞后”，再学习“执行状态 $\rightarrow$ 结构载荷”，比端到端地把命令直接映射到 My 更容易诊断和校准。

预测器输入不是当前 TD3 observation 的简单复制，而是带历史和候选计划的物理快照：

$$
z_t=\left(
x_{t-L+1:t},
u^{\mathrm{sent}}_{t-L+1:t-1},
U^{\mathrm{plan}}_{t:t+K-1},
\widehat L_{1:3,t}/L_{1:3,\mathrm{PID}}^{(s)},
\operatorname{condition}_t,
\operatorname{state}_t
\right).
$$

其中 $x_t$ 至少包括风速、转速、功率、实际电磁转矩、实际桨距、机舱加速度、三片 $|My|$、My 变化率和以 $\sin/\cos$ 表示的 azimuth；azimuth 相位对三片叶根载荷的不同峰值时刻是必要信息。$u^{\mathrm{sent}}$ 必须是经过 B4 residual、安全投影和速率限制后真正发往 Bladed 的 torque/pitch，而不是 Actor 原始输出。PID raw 里的动作采用 recorded PID demand；在线数据必须使用 Python 明确记录的实际发送动作，不能把当前 DLL 中作为 measurement alias 的 `O_*` 槽位当作在线 command。

未来窗口的载荷不只受当前 $u_t$ 影响，也受后续动作影响。因此每个样本都必须记录 $U^{\mathrm{plan}}$ 和 `plan_kind`。`realized_plan` 使用标签窗口内实际已发送的未来动作序列，只能在未来窗口闭合后用于离线/延迟执行器辅助监督和事后诊断；推理时不知道未来 Actor 动作，故它不能作为在线 shadow 输入，也不能比较候选 $\lambda$。第一版在线 shadow 与 candidate guard 只使用 `zoh_candidate`：在 $0.10$--$0.20\ \mathrm{s}$ 内保持当前经过投影的候选动作，且只有实际未来发送动作与该计划的偏差不超过冻结 `max_plan_mismatch` 的样本才能进入候选风险校准。$0.50\ \mathrm{s}$ 的 `realized_plan` 输出仅在窗口结束后做趋势诊断；B4 continuation 不在第一版 guard 中使用，因为没有对应的真实执行标签。PID raw 与在线数据混合前，必须先完成第 5 节的命令/实际转矩合同统一。

#### 9.6.2 训练数据如何同步产生

预测器有两类互补数据，二者都来自真实 Bladed 轨迹，不需要手动新增外扰：

| 数据源 | 用途 | 输入动作 | 监督标签 |
|---|---|---|---|
| `bladed-data-new/raw` PID 轨迹 | 离线预训练与执行器辅助监督；提供完整 23 case 覆盖 | 当前 PID demand 和标签窗口内实际 PID future action sequence，标为 `realized_plan` | 该时刻后 $H$ 秒内三片未来 $|My|$ 最大值与实际执行响应 |
| RL--Bladed 在线交互 | 覆盖 B4、Actor residual、投影和限速后的真实动作分布 | 当前和未来实际发送动作，记录 `realized_plan` 与 `zoh_candidate` plan-match | 后续 UDP 帧到达后形成的同一未来窗口峰值 |

每一时刻先暂存一个 pending 样本 $z_t$；未来 $H$ 秒的连续帧全部到达后，再补写 $y_{1:3,t}^{(H)}$ 并使样本可训练。跨 condition 边界、出现 UDP timeout、帧不连续、动作未成功发送或未来窗口不完整时，丢弃该 pending 样本，不能用零值或跨 case 的 My 补标签。

PID raw 的 23 条 $600\ \mathrm{s}$ 轨迹可为每个 $H$ 提供约 69 万个短时 `realized_plan` 监督窗口；它足以初始化模型，但只覆盖 PID 行为。只有 $0.10/0.20$ s 内实际未来动作满足 `max_plan_mismatch` 的窗口才能构成 `zoh_candidate` 校准样本。在线 RL 数据仍是必需的，因为预测器最终要评估的是 RL 的实际发送动作，不能仅凭 PID action 分布外推。

shared interface、dataset manifest、replay/loader/trainer 工具作为合同/通用离线代码保留。shadow JSONL 转换、Actor-frozen 独立 calibration/coverage 只有 synthetic fixtures，真实 Bladed shadow 数据尚无；`run_queue_training()` 不在线更新 predictor 权重，也未授权 guard。TD3 replay 不保存三片 My、pending 窗口或未来峰值标签；也不能因 TD3 fallback filter 而丢弃物理 shadow 所需的有效响应数据。

#### 9.6.3 预测器的训练与校准合同

预测器的监督 loss 与 TD3 actor/critic loss 必须完全解耦：预测器更新不得向 Actor 或 Critic 反向传播，也不得直接改变 TD3 的 Q target。它只从同一条 Bladed 交互数据流学习“状态和实际动作 $\rightarrow$ 未来载荷”。

运行前先用 PID raw 离线预训练。运行中，在动作已经发往 Bladed、等待下一 UDP 帧的间隙，允许执行有固定时间预算的预测器更新；不得延迟本控制步的动作发送。在线训练同时保留一部分 PID raw 样本，防止模型只适应早期 Actor/B4 动作后遗忘 PID 基准分布。混合比例、更新频率、batch size 和最大计算时间必须写入 config 与实验日志，不能在完整实验中临时修改。

安全干预使用预测上界而不是预测均值。对每片叶根、每个运行状态和每个预测窗口，在未参与该次模型更新的时序验证样本上计算非负校准余量 $q_{j,r,H}$：

$$
\overline y_{j,t}^{(H)}=
\widehat y_{j,t}^{(H)}+q_{j,r,H}.
$$

其中 $q_{j,r,H}$ 应是预先注册覆盖目标所对应的单侧 split-conformal 预测残差分位数；它必须由严格晚于训练数据的样本或冻结模型后的独立 case 计算，而不是用训练 batch 的平均误差替代。`load_guard_calibration.json` 必须按 `(blade, optimization_state, horizon, plan_kind)` 保存 `coverage_target`、`confidence_level`、`minimum_samples_per_group`、`max_plan_mismatch`、quantile rank、group count、经验覆盖率和下置信界。是否可启用预测器，取决于每个启用分组的上界漏报率和下置信界，而不是平均 MAE；任一字段缺失、样本不足、plan mismatch 超限或覆盖不达标时，`soft` 必须退回 `shadow`。

建议将以下状态写入每个 round checkpoint：预测器权重、optimizer、normalization、校准余量、pending 样本元数据、已标注样本数、PID/在线样本比例和各分组的上界覆盖统计。恢复训练时必须一起恢复；只恢复 TD3 而重置预测器会使后续 guard 的统计含义失效。

#### 9.6.4 何时开启，何时开始干预动作

以下是**后续验证计划，不是本次 diagnostic 的执行记录**。预测器应在取得生产模型后先离线预训练；不能在第一次预测后就取得动作干预权。建议采用以下固定阶段：

| 阶段 | 预测器状态 | 是否影响动作 | 最低要求 |
|---|---|---|---|
| A：离线预训练 | 仅使用 PID raw | 否 | 生成逐 `condition_id + 时间窗` 的 PID peak reference，并完成基础拟合。 |
| B：首次完整改造后的 V1/V2 影子模式 | 继续收集 B4/BC/Actor 的在线标签 | 否 | 记录每片叶根、每个状态、每个 $H$、每种 `plan_kind` 的预测误差与上界覆盖；不改变任何 torque/pitch。 |
| C：V3 在线校准模式 | 混合 PID raw 与在线已标注样本更新 | 否 | 验证样本必须与本轮模型更新分离；仅 `zoh_candidate` 的 $0.10/0.20$ s plan-match 样本可进入 soft 校准。 |
| D：软干预模式 | 冻结 `load_guard_calibration.json`，预测器继续仅影子更新或在轮末更新 | 是，缩小 residual | 仅在每个启用分组都通过 calibration artifact gate 后，且只从 Actor residual 中撤回风险部分。 |
| E：硬 guard 候选 | 预测器和校准余量冻结 | 是，作为独立安全监督候选 | 必须在另一轮独立的固定 case 验证中证明上界覆盖、动作时延和误报率满足预注册要求。 |

是否允许 `soft` 不能按“训练到了第几轮”硬编码，也不能用一个未定义的 `load_predictor_ready` 布尔量替代。唯一允许的启用依据是冻结的 `load_guard_calibration.json`：每个启用的叶根、状态、$0.10/0.20$ s horizon 和 `zoh_candidate` 分组均有足够样本、plan mismatch 合格、上界覆盖下置信界达标、输入动作合同一致、预测器更新未造成 UDP 时延或新的 timeout，且当前 case 具有 `strict_case_matched` 的 PID reference/time window。任一条件不满足，预测器继续影子运行，不干预动作。

在当前计划中，所有代码和离线 artifact 完成后，V1/V2 固定只做 `zoh_candidate` 在线影子采集和 `realized_plan` 延迟诊断，V3 才产生可冻结的 calibration artifact；即使中途收集到足够数据，也不能在同一次运行中切换到 soft。硬 guard 不应在同一次首次 soft 训练中开启，必须留给冻结后的独立验证 run。若 Actor optimizer 被冻结或 case 执行 B4/recovery，预测器仍可记录真实载荷，但这些记录必须带 execution mode，不能被误解为 Actor candidate 风险验证。

#### 9.6.5 软干预的具体动作规则

设 $r_t$ 为 Actor residual，$a_{B4,t}$ 为同一步 B4 action。对一组固定候选缩放系数

$$
\Lambda=\{1,0.5,0.25,0\},
$$

先经过与正常动作相同的投影和速率限制，得到候选实际动作：

$$
a_t^{(\lambda)}=
\operatorname{project}\left(a_{B4,t}+\lambda r_t\right),
\qquad \lambda\in\Lambda.
$$

对通过 `zoh_candidate` 校准的 $0.10/0.20$ s 窗口，预测器选择最大的可行 $\lambda$：

$$
\lambda_t^*=\max\left\{
\lambda\in\Lambda:
\overline y_{j,t}^{(H)}(a_t^{(\lambda)})
\leq1+\epsilon_j,
\ \forall j,\ \forall H\in\{0.10,0.20\}\ \mathrm{s}
\right\}.
$$

这意味着优先保留能够带来功率收益的 residual，只有预测到短时峰值有风险时才逐级缩小，而不是一有风险就无条件把所有动作替换成 PID。每次干预至少记录：`load_guard_active`、`load_guard_lambda`、预测窗口、触发叶根、预测上界、当前 peak ratio、PID reference、候选动作与最终发送动作。

若 $\lambda=0$ 的 B4 action 也不满足预测约束，系统必须记录 `load_guard_no_feasible_action=1`。此时不能把 B4 称为已验证的安全动作，更不能伪造一个未经验证的“安全” torque/pitch；应保持现有物理保护链，并将该 case 标记为不具备“不超 PID 峰值”声明资格。只有后续有经验证的保守保护动作或更可靠预测模型时，才讨论进一步自动处理。

预测器干预后的 replay 必须保存实际发送动作，并单独记录 `load_guard_active`；不能复用当前 `control_fallback_active` 将这类样本全部过滤掉，否则会再次制造“保护触发后没有数据可学”的断流。

#### 9.6.6 理论可行性与不确定性

该方案的理论基础是成立的：固定 case 的 PID raw 给出了可行基准与初始载荷响应，Bladed 在线交互会持续补充 RL 实际动作下的响应。它有机会把“峰值事后扣分”升级为“动作前风险缩放”，但它不是现成的峰值保证。当前不确定性应明确分层：

| 项目 | 当前判断 | 不确定性 |
|---|---|---|
| PID raw 构造离线短时标签 | 可直接实施 | 低 |
| 与 RL--Bladed 交互同步采集、延迟标注和影子更新 | 独立 pending replay 已有；仍需接入在线训练、持久化并校准生产预测器 | 中等 |
| 预测既有 23 个 case 中 PID/B4 附近的短时 My | 有 raw 和在线数据支撑 | 中等 |
| 预测未充分覆盖的 Actor residual 响应 | 初期需要依赖保守余量 | 高 |
| 用预测结果缩小 residual | 可在软干预阶段验证 | 中高 |
| 声称每片叶根绝不超过 PID 峰值 | 当前不能承诺 | 高，需冻结模型后的独立验证 |

不确定性的主要来源不是“缺少手动外扰”，而是 PID raw 只覆盖 PID 动作、峰值上升很快、当前控制只有发电机转矩与集体桨距两个自由度，以及长期在线更新可能改变预测误差分布。故预测器的正确路线是：先影子、再软缩放、最后独立验证；不能跳过中间校准阶段。

### 9.7 训练和验收流程

对当前 23 个既有 case，严格按以下顺序运行：

1. 复核并冻结**已有** `condition_id -> PID raw CSV SHA-256 -> 时间窗` 映射，不手动改变当前 GUI Batch Run 的风、波浪、yaw、电网或外载荷设置；后续新场景需另行生成工件，不覆盖本次参考。
2. 使用**已有**的 exact 600 s / 180 s paired PID power/load reference；在每个在线 condition instance 对完整 Time + wind trace 做 strict identity 校验，不把本次 prefix 校验报告改名为正式结果。
3. 使用已构建的 PID 预测数据集和独立 pending replay，完成 production 短时预测器的离线训练、冻结与时序 holdout；之后的 V1/V2 固定以 shadow 模式收集真实 Bladed 标签，此阶段不让预测器改变动作。本次训练的 shadow 配置字段**不等于**已完成生产预测器训练。
4. 严格匹配时间窗：$600\ \mathrm{s}$ full run 使用现有 $[0,600]\ \mathrm{s}$ PID reference；$180\ \mathrm{s}$ smoke 使用现有 $[0,180]\ \mathrm{s}$ PID reference；同时验证配置/检查点指纹和原始 CSV 哈希。
5. 只有 V3 后生成的冻结 `load_guard_calibration.json` 对所有启用 `zoh_candidate` 分组通过时，才在独立 config 的后续 run 软缩小 residual；第一次包含预测器干预的 run 不授予硬 guard 资格。
6. 逐场景报告 $\Delta E^{(s)}$、$\Delta L_1^{(s)}$、$\Delta L_2^{(s)}$、$\Delta L_3^{(s)}$、$g_1^{(s)}$、$g_2^{(s)}$、$g_3^{(s)}$、预测上界覆盖、`load_guard_*` 和所有 fallback/guard 原因。之后才按 [控制策略指标_更新版.md](控制策略指标_更新版.md) 聚合最终通过判定。

禁止以下做法：

- 在 PID 与 RL 对照之间手动改变当前 Batch case 的风、波浪、yaw、电网或外载荷设置。
- 用 $600\ \mathrm{s}$ PID 峰值评价 $180\ \mathrm{s}$ RL 轨迹，或比较不同起止时间窗。
- 仅在 Python reward 中虚构外力/My 变化，而不让 Bladed 动力学参与。
- 只报告三叶根平均降幅而不报告单片叶根是否超 PID。
- 在 RL 结果出现后再修改 PID reference、时间窗、容差或扰动定义。

本节下一阶段仍不需要新增外扰：先**复用现有** 23 场景 paired PID reference、state20 逐工况诊断与短时预测器离线数据，完成生产模型训练、在线 shadow 覆盖/校准及逐叶根峰值约束链的独立验证。只有该链稳定且后续具备固定复现新 case 的能力时，才考虑新增扰动场景；它不属于当前实现范围。

具体的开发边界、一次性改造内容、离线验收和改造完成后的 Bladed 验证顺序见 [开发执行计划.md](开发执行计划.md)。
