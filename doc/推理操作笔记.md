## 1. 正式 state20 推理合同

正式 policy 路径为：state20 observation → 状态条件 B4 residual + 冻结 Actor → 安全投影/速率限制 → float64 demand → Bladed UDP。Actor 输出是归一化 residual，不是物理扭矩；物理 FIR shadow 是发送后诊断，不参加该动作链。

正式 Actor 使用 20 维 state-aware observation：10 个基础物理量、2 个上一步实际发送 demand、5 个 optimization-state one-hot 和 3 个 control-region one-hot。工程 request bounds 为 torque $21{,}586{,}451.33303$ Nm、pitch $0.43$ rad；不得用历史 12 维 observation、旧 normalization 或 `--inference-torque-high` 绕过 resolved contract。

## 5. queue strict identity 结果解释

正式 strict validator 使用：

```text
fixed simulation time offset
full Time + I_AverageWindSpeed trace
paired PID reference entry
optional project/case SHA-256 fingerprint
```

结果状态：

- `strict_case_matched`：完整 trace signature 或项目/case fingerprint 匹配。
- `reference_matched_only`：trace 与 reference 可比较，但没有足够的 strict project/case identity 证据；不得当作最强正式身份结论。
- `prefix_matched`：只完成 prefix 诊断时使用的描述；只能用于 debug，不能用于正式验收。

一旦固定 offset、时间戳或风速误差超过 tolerance，必须停止该 condition，不能继续收集 policy 指标。condition ID、instance ID、scenario ID 和 paired reference entry 必须一起写入结果。

## 7. PID 对比和报告边界

### 7.1 paired reference

PID 对比必须使用同一条 paired entry：

```text
same condition
same raw CSV provenance
same time window
same exact timestamps
same three blade My peak values
same Time + I_AverageWindSpeed signature
```

600 s inference 只能对比：

```text
RL/data/paired_pid_power_load_reference_3_to_25_600s_v2.json
```

180 s inference 只能对比：

```text
RL/data/paired_pid_power_load_reference_3_to_25_180s_v2.json
```

不能用 600 s 全程 peak 充当 180 s window 的严格 per-blade peak reference，也不能分别 lookup power 和 load。

### 7.2 当前可用 holdout

当前 raw_infer 有风况 `8/16/24`。这些结果可以说明 holdout 上的组件行为，但不能外推为全部风况的 formal acceptance。报告中必须同时给出：

```text
wind/condition ID
window start/end
PID paired reference hash
policy checkpoint fingerprint
strict identity status
per-blade peak and energy metrics
W5 shadow diagnostics
fallback/timeout/invalid counts
```

### 7.3 formal evaluator 与 release manifest

当前代码已有单场景 trapezoidal-energy / blade-peak evaluator、多场景 evaluator 以及 hash-bound release manifest；字段包括 `official_acceptance_pass`、`strict_per_blade_pass`、`comparison_tolerance_nm`、strict identity、T1 与 release gates。只有构造的测试 fixture 覆盖这些代码路径；真实 V1/V4 inference CSV、identity sidecar 和运行证据还未形成，所以**没有可用的物理 acceptance report 或 release manifest**。V1 integration report 不得冒充 23-case release。

## 8. DLL 和 Windows 状态

本轮未修改正式源码 [controller.cpp](../bladed_env/udptest/udptest/controller.cpp)，因此不需要重新编译 DLL。当前只检查 Windows 上 Bladed 实际加载的现有 binary（记录完整路径及 `Get-FileHash -Algorithm SHA256`）、queue-v2 协议和 rounds/schedule 是否与 V1 manifest 一致；这些证据尚未通过。该笔记不要求重新编译。

这意味着：

- 当前 DLL stdout 日志不可作为审计来源；不要再增加或依赖 `printf` 日志。
- 当前 DLL 没有可供 Python 使用的 torque set 返回码/readback 结构化 telemetry。
- `O_PcsTorqueDemand` 和 `O_PitchPositionDemand1` 仍是当前 DLL 暴露的 measurement alias，不代表 Python 已收到 command readback。
- `I_ElectricalTorque` 才是实际执行反馈字段。
- Windows DLL 文件已存在；仍需确认实际加载的 DLL 身份，并完成 UDP protocol validation。源码未变不等于协议 gate 自动通过。
