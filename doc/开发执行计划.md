## 0. 执行原则

本计划采用“一次性完整开发，离线验收通过后才由小到大验证 Bladed”的方式；V1--V4 是**开发完成后的验证阶段**，不是开发期间的调参循环。

1. 开发期间只允许版本化静态合同、已有约 $251\ \mathrm{kB}$ 的逐工况指标、分块/流式历史诊断、单元/集成模拟测试、raw 与 `raw_infer` 离线分析、工件构建及无 UDP 的 evaluator 回放；当前不训练/加载 NN 载荷模型，不运行任何 BC-only、短时 smoke 或全量 Bladed 闭环来指导本轮代码修改。
2. 在动代码前预注册诊断假设和比较口径：风况 10--12 的累计电量缺口、14/15/18 的逐叶根超峰、3/4 的启动/恢复、recovery 的 Critic batch 抽样，以及第 4 轮仍增长的 target-Q。末轮 replay recovery **存量约 $1.0\%$、按源等机会抽样约 $34.8\%$ 是推算而非实测**；不得先认定其为性能因果根源，再据此随意调整权重或 Q 阈值。
3. 保留原 state20 的指纹与 checkpoint 作为冻结对照。仅当状态、动作、B4、PID reference、BC 数据或观测定义**实际变动**时，按依赖图重建受影响的全部派生工件、归一化、checkpoint 和配置；不覆盖本次历史目录，不用旧 obs12/旧 $21\ \mathrm{MNm}$ checkpoint 冒充新合同。训练日志与训练中的 checkpoint 属诊断，**不能充当固定策略的独立验收轨迹**。
4. 所有 W0--W6 的剩余代码、候选配置、测试、资源预算、Windows DLL 编译/协议校验一并通过第 4 节离线门禁后，才允许首次 Bladed V1。V1--V4 中若需改 reward、模型、状态、采样、阈值、时间窗、DLL 排程或日志合同，停止旧版本、重新命名/冻结新版本并从离线门禁及 V1 重来；不得一边跑一边改参数。
5. 当前唯一载荷旁路是 `physical_fir_v2` 只读开发 shadow。任何未来 NN 预测器都是新批准的独立研究，不属于当前发行版；无预测覆盖/严格身份/独立校准时，不开放 soft/hard。
6. 任何大数据处理采用按行扫描、按 condition/时间窗有界抽取或磁盘映射。旧 state20 实验目录约 $81\ \mathrm{GB}$，两张逐步长表约 $40.8/40.6\ \mathrm{GB}$；不可用编辑器、`pandas.read_csv` 或绘图脚本一次加载整表。新日志必须保留逐 condition/round 证据，同时限定内存和磁盘；只切换 `compact_streaming` 而丢掉逐 condition 汇总不算完成。

## 1. 冻结的范围与合同

### 1.1 场景合同

当前范围只复用已有的 23 个 Bladed case，不新增或手工调节风、湍流、波浪、yaw、电网或外载荷。state20 的 $180/600\ \mathrm{s}$ paired PID power/load reference **已经生成**；必须区分已冻结的 PID reference 身份与每个在线 Bladed case 的实际身份，二者缺一不可。不能再把“生成 paired reference”当作 W4 的未完成任务。

PID reference 身份为：

```text
scenario_id
condition_id
PID raw CSV path
PID raw SHA-256
time_window_start_s
time_window_end_s
```

在线 case 身份另含：

```text
queue condition_id + condition_instance_id
Bladed case/project fingerprint（可获得时）
fixed simulation-time offset
canonical wind-trace signature
```

`condition_instance_id` 属于运行时 queue slot，**不是** paired PID reference 的检索键。训练侧已有 prefix/strict 两级 validator，但这次 diagnostic 配置采用前 3 帧风速前缀比较；无后缀的 strict 配置虽然存在，**尚不能反向提升本次历史 run 的身份级别**。下一轮训练和独立推理都要在每个 condition 开始时校验静态 `condition_id`、raw SHA、窗口及 queue slot，在运行中按固定 offset 累积 `Time + I_AverageWindSpeed` canonical signature，并于 condition 结束时比对完整参考或可验证的 project/case fingerprint。失败即该场景无效并禁止正式结论；只有严格匹配才可标记 `strict_case_matched`，仅前缀/静态 reference 匹配仍为 non-release diagnostic。

PID、B4、BC、Actor、载荷预测器和最终评估必须使用兼容的参考身份；训练/评估结果还必须记录对应的在线 case 身份。$600\ \mathrm{s}$ run 使用已生成的 $[0,600]\ \mathrm{s}$ 工件，$180\ \mathrm{s}$ run 使用已生成的同源 $[0,180]\ \mathrm{s}$ 工件；不得用 $600\ \mathrm{s}$ 的 PID 峰值替代短窗口峰值，也不得混用训练数据与 `raw_infer` holdout。

### 1.2 torque 与执行响应合同

| 对象 | 冻结定义 | 用途 | 不可混用为 |
|---|---|---|---|
| PID/Actor demand | `O_PcsTorqueDemand`、Python `sent_action_torque`，范围 $[0,21{,}586{,}451.33303]$ Nm | B4、BC、Actor、safe envelope、previous-action history 的动作合同 | `I_ElectricalTorque` |
| 实际电磁转矩 | `I_ElectricalTorque`，当前 Bladed 响应最多约 $21{,}000{,}000$ Nm | 功率计算、执行器响应建模、低速保护、载荷预测器输入 | Python demand 上限 |
| 正常运行桨距 | $[0,0.43]$ rad | B4、BC、Actor 的正常发电包络 | 物理 feather 上限 |
| $22$ MNm inference | 接口余量诊断 | 已验证 API 路径不会在 $21$ MNm 截断 | 训练或部署动作上限 |

形式上：

$$
T_{\mathrm{request}}\leq21{,}586{,}451.33303\ \mathrm{Nm},
\qquad
T_{\mathrm{actual}}=I_{\mathrm{ElectricalTorque}}\lesssim21{,}000{,}000\ \mathrm{Nm}.
$$

这里保留 `I_ElectricalTorque` 并不表示 Python 再保留一个 $21$ MNm clip。它是被控对象返回的实际响应：请求继续增大时，它能说明电气/传动链是否已饱和，并决定真实功率和后续 My 如何响应。previous-action observation 必须归一化实际发送的 demand，不得改为归一化实际电磁转矩。

`torqueDemandMax=21` MNm 保持为当前 Bladed 被控对象的参数，不在本计划中修改。修改它会改变 PID raw 对照所对应的对象，届时必须重新生成 PID 与 RL 的全部可比数据。

state20 已将工程请求上限 `engineering_demand_high_nm=21,586,451.33303` 接入 controller projection、最终 clip 与 UDP wire serialization 的 `float64` 边界，改动后仍须回归测试；神经网络的 `float32` residual 在解码边界立即转换为 `float64`。`float32(21,586,451.33303)=21,586,452` 会在字面上高出上限约 $0.667$ Nm。raw 中的 $21,586,452$ Nm PID label 已按原始记录与有效 clip 值区分；不得把实际 `I_ElectricalTorque` 的 $21\ \mathrm{MNm}$ 限幅误当成 request high，也不得把历史已解决的 $21\ \mathrm{MNm}$ 截断重新引入新训练。

### 1.3 运行状态与策略边界合同

优化状态固定为以下四类，另保留一个不参与优化的异常安全状态：

| 状态 | residual 策略职责 | 优化优先级 |
|---|---|---|
| startup/stopped | 不探索 residual，使用 B4/PID 恢复路径 | 可启动、可恢复、无异常动作 |
| below-rated | 使用状态软包络 | 提升累计电量，同时守住逐叶根峰值 |
| transition | 使用连续插值的软包络 | 功率、转速、桨距、载荷连续 |
| above-rated | 使用状态软包络 | 降低逐叶根极限 My，同时守住累计电量 |
| negative-power abnormal | 不执行 Actor residual，进入独立保护/终止语义 | 数据完整性与安全处置 |

`startup/stopped` 是对现有启动与停机状态的优化层合并，不删除底层的 `startup_cut_in`、`shutdown_stopped` 或 `negative_power_abnormal` 原始状态码。状态机必须因果：v1 使用滤波风速作为区域前瞻，并以转子转速、真实功率和持续时间判断是否允许进入优化状态；实际桨距和上一发送动作保留为连续控制/包络输入，而不在没有校准规则时伪造新的离散阈值。

上述因果状态机、20 维观测与版本化 `state_calibration_v1` **已实现**，当前冻结值为：`wind_filter_time_constant_s=2.0`、`region_confirmation_s=1.0`、transition enter/exit $11.8/11.2$ m/s、above enter/exit $13.8/13.2$ m/s、running/stopped rotor speed $0.5/0.4$ rad/s、generation/stopped power threshold $100{,}000$ W、negative-power threshold $-1{,}000$ W、running/stopped confirmation 均 $1.0$ s。control region 仍主要依赖滤波风速，须在风况 10--15 的功率/峰值事件邻域核对运行态确认与 residual 准入；**仅有可复现误分区证据时**改阈值、生成新版本并重建所有依赖工件。`raw_infer` 仍仅用于离线验证，不回流训练。

已有的状态软**残差幅度**包络为：below torque $\pm15$ kNm、pitch $\pm0.00030$ rad；transition $\pm15$ kNm、$\pm0.00035$ rad；above $\pm20$ kNm、$\pm0.00035$ rad，Actor 输出再按 `actor_residual_target_scale=0.25` 缩放。startup/stopped/negative-power 的残差包络为零，状态切换采用插值。它不是最终发送命令的“软速率”：B4 自身随时间改变，最终仍受工程 $90$ kNm/step、$0.000698$ rad/step 的变化限幅与保护链约束。任何扩大幅度的提案先离线证明必要性，不以 raw 极值直接放宽。

### 1.4 载荷与最终验收合同

工程目标按每片叶根约束；官方验收使用三叶根**极限值降幅**平均，不以平均 My、RMS、p95 或逐时刻 My 差替代。state20 当前有 `my_peak_increment`、超峰后持续 `pid_excess` 和轮末 `DualConstraintController`，但这些是**事后软训练信号**，并非经过校准的动作前物理保证。对每个场景 $s$：

$$
L_{j,\mathrm{RL}}^{(s)}
\leq
L_{j,\mathrm{PID}}^{(s)}(1+\epsilon_j),
\qquad j\in\{1,2,3\}.
$$

本计划的严格工程 gate 默认冻结为 $\epsilon_j=0$。若项目接受数值容差，必须在首次 Bladed 验证前写入版本化 config 和报告模板，不能在查看结果后修改。

最终项目验收仍使用 [控制策略指标_更新版.md](控制策略指标_更新版.md) 的累计电量和三叶根平均载荷降幅：

$$
(P_1\land L_0)\lor(L_1\land P_0).
$$

因此最终报告必须同时给出官方平均指标与逐叶根严格 gate；任何一片超出严格 gate 时，不得用另外两片的改善掩盖风险。

正式 evaluator 应输出两个**不混淆**的布尔结论：`official_acceptance_pass` 按 $(P_1\land L_0)\lor(L_1\land P_0)$ 判断，`strict_per_blade_pass` 按逐叶根 $\epsilon_j$ 判断。默认 $\epsilon_j=0$ 是额外严格工程 gate；浮点舍入只允许单独记录的 `comparison_tolerance_nm`，不得伪装为事后放宽的物理容差。逐场景能量必须对同窗严格递增时间戳的实测功率做**梯形积分**，每片叶根取 $\max|My|$；训练逐步 $P\Delta t$ 及跨 92 条轨迹“平均峰值之比”只能作诊断。**本计划默认的发布层总闸是 23/23 个预定 case 均具有完整且严格匹配的独立冻结策略轨迹，每个 case 的官方路径通过且三叶根逐片 gate 均通过；另把边缘频率/T1 作独立部署闸。**这条“全场景+逐片”是比单轨迹官方公式更严的**工程发布标准**，不要把它伪装成官方公式本身；如果项目正式合同规定不同跨风况聚合，必须在 V1 前审批并固定其公式、重复次数、无效/缺失场景处置和比较容差，不得因 V4b 不达标才改用更有利的平均。训练中的移动策略不算独立候选策略。

## 2. 目标架构

主链保持现有 B4 residual TD3+BC，不新建第二个 Actor；一次性开发的新增模块必须用同一冻结合同关联：

```text
fixed raw/raw_infer
  -> 已有 paired PID reference / state20 artifact / BC (fingerprint 冻结)
  -> 针对高风险工况的有界事件分析 + 无 UDP 反事实代理回放（不可伪装物理结果）
  -> 一次性完成 replay/source 审计、reward 对齐、在线 predictor/guard 和 compact evaluator
  -> 冻结的 B4-centered state20 TD3+BC -> controller projection / low-speed protection / sent demand
  -> Bladed actual response and My
  -> strict case identity + paired PID 梯形电量/逐片峰值验收 + predictor shadow/后续校准
```

| V3 | 全 23 风况 × 2 轮 × $600\ \mathrm{s}$，先覆盖混合状态/Q 门控 | R2 共用 profile builder 使用 `--rounds 2` 生成 46-slot manifest；Windows DLL `profile=full` + `ROUNDS=2`，两端由 schedule hash 绑定。round count 是配置值，不另建 `full_23x2`/23×2 profile branch；update count 由统一 validator 重算。Windows compile/protocol/T1 实测 gate 仍须单独通过 |
| V4a/V4b | V4a 全 23 × 4 × 600 strict **训练**；V4b 从冻结 checkpoint 做覆盖所有 23 case 的**独立策略推理** | 23×4 strict 训练配置已有但 `policy_acceptance=false`；独立推理可预注册 23×1 full（DLL 输入 `full` + rounds=1 形成报告身份 `full_23x1`，Linux 必须在 W6 新增严格 profile，23 slots），或预先冻结 23×4 strict 复测（92 slots）；不能事后择优选范围 |

`smoke_4x4` **只包含 8/11/12/16**，不代表低风 3/4 或载荷峰值风险 14/15/18；这些必须在 V3/V4 的全部 23 风况中覆盖。若项目确需在 V1 前单独覆盖这些风况，应在 W6 **开发阶段**同步实现、编译和测试新的 DLL schedule、Linux manifest/strict 配置并写入冻结表；`--condition-id` 只改变输出命名，**不能**选择物理 Bladed case。未完成这一增量时不得在 V1 报告“已测 wind3/14/15”。

### V1：小规模集成与覆盖验证

目的不是重复历史 B4-vs-Actor 闭环调参，而是用**已冻结**的 BC warmstart 或 B4 对照及单独的策略 checkpoint 在固定 4 风况 $180\ \mathrm{s}$ 下验证控制合同和严格身份。V1 不做在线 Actor/Critic 更新；基线与策略对比必须用不同 Bladed run ID，但配对参考与窗口完全一致。每个 4×4 推理 run 均应执行 **`--episodes=16`**（queue 模式指 16 个已完成 TRAIN slot，默认 `--episodes=1` 不能覆盖全 4 轮）。冻结的 PID 预训练预测器在 shadow 中记录有效预测/延迟与 pending 标签，**不干预动作**；若加载/数值验证失败，仅能按 `shadow_no_prediction` 继续受保护采集并标记 V1 未通过，不能据此推进 V2。

逐 condition 检查需求上限 $21.58645133303\ \mathrm{MNm}$、实际电磁转矩反馈、桨距/速率、安全投影、状态机、OOD/保护模式、trace 时间戳/风轨完整匹配、reference/实例哈希与 compact 指标；当前 DLL 固定顺序必须与 manifest 一致。**通过门禁：**4/4 个条件、16/16 个预定 slot 均完整、无 invalid/timeout/错帧/合同不匹配、严格身份全通过、逐工况 E/My/执行模式与报告全落盘；只验证集成正确性，不要求从四个条件外推功率/载荷达标。失败即归档/新版本返工，不能在本次 V1 中临时调门控。

### V2：小规模训练行为验证

V1 完成后，用已冻结的 **4×4×600 strict** 合同验证一轮收集、后三轮更新的 TD3+BC/双约束、replay source quota、optimizer gate、compact 和生产 predictor 的**在线 shadow 数据流**；不因状态分布有限而宣称全面性能改善。计划之外的新增风况不靠 Linux JSON 临时指定。达到完整 condition 后才更新轮末乘子，不能把已发生的超峰解释为硬安全合格；若另行安排冻结策略对照推理，4×4 全覆盖同样要求 **`--episodes=16`** 和新的 batch run ID。

**通过门禁：**队列全覆盖且无 skip/retry、严格身份通过、`scheduled=critic_executed+critic_skipped_by_reason` 与 Actor 尝试守恒、真实 batch source 计数和 quota-relax 可核、无长期 Q hard guard/optimizer gate 死锁或已解释并批准的任何超限；每条件功率/逐片峰值/状态/奖励与训练时长完整。shadow 的真实发送动作/未来标签必须时间因果、plan-match 可核、无跨 condition 污染；未满足独立校准/严格身份时保持不改动作。V2 训练 checkpoint 另起独立冻结推理流程才可评价物理策略效果。

### V3：中等规模全风况长期验证

使用 W6 **预先开发**的 23×2×600 strict profile（DLL `full` + rounds=2 与 46-slot Linux manifest 匹配）观察混合状态下的 Q/TD/Q-gap、低速恢复、状态误分区、风况 10--12 功率缺口与 14/15/18 三叶根峰值、预测器的在线 shadow/plan-match；第 1 轮收集、第 2 轮更新，名义调度约 23,000 次，实际以 condition boundary/step 审计值为准。报告相对于 historical diagnostic 的指标，但不同版本/噪声/时间窗不得被当作已证实的因果改善。

**通过门禁：**23/23 条 condition 各轮完整、严格身份逐 slot 通过，训练/通信无完整性故障，所有场景有训练电量代理、真实可用于正式评价的完整轨迹、逐片峰值、执行模式、batch source 和 predictor coverage；资源上限满足冻结预算。V1--V3 获得足够真实 RL `zoh_candidate` 样本后，**在 V3 结束并冻结生产预测器权重之后**用与训练样本分离的后续/独立时序校准集派生 `load_guard_calibration`，逐 `(blade,state,horizon,plan_kind)` 检查下置信界/样本数/失配；无合格 artifact 就继续 shadow，不因为到 V3 自动 soft。需要补数据则另排经批准的新独立 shadow run，不在 V3 现场调算法。

### V4：完整训练与最终验收

**V4a，训练：**以冻结的 23×4×600 strict profile 运行全量 TD3+BC；默认保持 shadow。即使 V3 后有合格的冻结校准，**只有每个发送前能够可靠核验当前 case/project 身份**、候选计划风险与现有安全保护均通过，才可为 soft 生成另一个预注册 config/全新 run ID 的独立策略分支；只有终帧 full-trace 签名、没有发送前身份凭证时，该分支仍必须保持 shadow。不得在同一训练中途从 shadow 切换；不同分支不能混在同一验收轨迹。hard_candidate 需要后续另外一轮冻结验证，本阶段不给资格。

**V4b，独立冻结策略评估：**V4a 完成后根据**预先登记的固定 checkpoint 选择规则**锁定 Actor（不能看 V4b 的结果再择优轮次），生成 23×1×600 严格**推理** manifest/Windows `full`+rounds=1 及 `--episodes=23` 对应的完整场景证据；若项目预注册要求 4 次重复，则使用 23×4×600 strict 的**独立推理**并设 `--episodes=92`，而非训练过程同一批轨迹。每个输出必须完整结束、采用新的 batch run ID、独立严格 runtime identity 与同窗 PID 梯形电量；有任何 condition 缺失/失配，整批不得作为正式结论。训练端无后缀 strict config 的 `policy_acceptance=false` 仍只表示模型候选运行，**不自动授权 release**；只有 V4b evaluator + release gate 可给出最终双结论。

最终报告必须逐场景给出（由基础单轨迹公式扩展成多场景官方 evaluator）：

```text
scenario identity and reference hash
E_PID / E_RL / Delta E
L_PID,j / L_RL,j / Delta L_j for j=1,2,3
official average Delta L and official_acceptance_pass
strict per-blade epsilon_j gate and strict_per_blade_pass
state occupancy
inference execution-mode counts and training checkpoint's replay/batch-source accounting（分开报告）
guard/skip/retry accounting
Critic hard Q guard and Actor optimizer gate status (trend gate only if actually instantiated)
load_guard status, prediction/plan-match/coverage (or explicit unavailable status)
latency and output-frequency result
```

只有场景、时间窗、reference/运行 trace 身份、冻结 checkpoint、动作合同均有效时，才对每个有效场景按**同窗梯形积分累计电量**与三叶根 $\max|My|$ 判定：

$$
(P_1\land L_0)\lor(L_1\land P_0)
$$

判定官方性能通过；另外单独报告逐叶根严格 gate。总体判定仅依赖 V1 前冻结的场景覆盖/跨场景规则：不将 92 条训练中的平均峰值比 $-4.63\%$ 或训练 $-0.712\%$ 当作正式结果。若正式未通过，仍可完整归档诊断及证据；该版本不能标记发布，也不得在本次 V4b 结果出现后修改时间窗/容差/聚合规则。

## 7. 实施完成定义

**开发完成 / 允许启动 V1（不是宣称策略达标）的充要检查清单：**

1. 上游状态/动作/B4/paired PID/BC 已签名冻结或依变更正确重建；20 维状态、$21.58645133303\ \mathrm{MNm}$ float64 请求、上游新旧 fingerprint 阻断及 `raw_infer` 独立性均可机检。
2. W2/W3 的逐条件 E/My/状态与更新/sampling/门控统计闭合，静态配置明确 quota、dual 参数、有效 gate、负例/异常处理；compact 流式日志在模拟完整 92 slot 后仍可复算逐场景代理指标而不会写出 $40\ \mathrm{GB}$ 级长表。
3. W5 的生产 predictor 模型必须证明其**以同一语义的候选 action plan 条件化**（若既有 history 末帧动作足以表达 ZOH 计划，需提供等效性与多窗口/多 $\lambda$ 回归测试；否则更改静态接口并重建依赖指纹），有可审计 PID train/holdout 切分、加载/恢复/在线 pending/shadow 与多窗口软/硬校准准入的完整测试。首次 V1 **默认 shadow**，可尚无真实 RL 校准而无 soft/hard 资格，但须有有效冻结 PID shadow 模型，不能“空模型却报告有效预测”。
4. W6 的训练与冻结策略推理均有 strict identity 代码及负例测试，正式 evaluator 输出逐场景梯形电量、三片峰值、官方与逐片双结论及候选/发布 manifest；未满足严格场景身份/完整 trace/冻结模型时禁止标为 release。生成器已生成匹配 DLL 的 4×4、23×2、23×4 及预注册的 23×1（若选此正式评价档）配置/manifest，Windows 目标 DLL 已编译部署、协议兼容。
5. 全量 `wind` 环境 unittest、新增回放/日志/评估资源测试、Windows 端编译和无 Bladed 协议检查全部通过；V1--V4 的 case 顺序、run ID 策略、paired 窗口、比较容差、$\epsilon_j$、Q/replay/guard 规则、跨场景合格口径、checkpoint 选择规则、日志内存/磁盘预算及报告模板全部在首次 V1 前预注册并冻结。

满足以上五项后才允许 V1→V2→V3→V4a 训练→V4b 冻结策略独立推理。每一阶段都可能因合同/安全/身份或官方指标失败而停止；停止不构成“半成品开发流程堵塞”，而是一次性开发后的**有证据验收**。V4b 不达标则如实归档，不宣称本版策略发布；新增设计另起合同版本并重新走第 4 节与 V1。不能用“已完成训练”“Q gate 没报警”或未校准 predictor 的可运行性代替物理指标验收。
